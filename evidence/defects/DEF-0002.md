## Mechanism

WinForms' default UIA provider derives `AutomationId` from
`Control.Name` — **the property**, which is distinct from the C# field name.
These designers are hand-written and declare fields well:

```csharp
// PharmaX.Desktop/Features/Login/frmLogin.Designer.cs — the good pattern
private TextBox txtUsername = null!;
...
txtUsername.Name = "txtUsername";     // ← this line is what creates the AutomationId
```

All 41 designer files assign `.Name` for *some* children, so the pattern is
understood and applied — but inconsistently. 146 interactive controls are
declared with a perfectly good field name and never receive the assignment, so
they reach the UIA tree with an empty `AutomationId`.

**This is not the "generated designer names" problem.** Field naming here is
genuinely good. The defect is a missing one-line assignment per control, which
makes it mechanical to fix — but it is not cosmetic, because it changes what the
test suite can address.

## Impact

Three specific consequences, in increasing order of seriousness:

1. **Assertion quality.** §Q requires assertions on the accessibility tree and
   forbids reading values out of pixels. With `frmProductEdit`'s nine fields
   unaddressable, INV product-master assertions would have to be made from
   screenshots — which §Q prohibits and which cannot distinguish `12.00` from
   `12.0O`.

2. **Self-referential UI defect.** §I.13 makes coordinate-only reachability a
   UI-conformance failure. W11 would therefore fail 31 of 46 forms on item 13
   regardless of what the forms look like — the conformance sweep would be
   measuring this defect rather than the UI.

3. **Modal escalation is the worst case.** `frmSupervisorPrompt` is the
   escalation modal for Section E axis 7 (discount above limit, price override,
   variance). It has 8 `.Name` assignments, so it is in better shape than most —
   but its parent flows (`frmTillSession`, `frmGoodsReceipt`, `frmClaims`)
   cannot be driven by id to *reach* the escalation, so the axis-7 cases are
   blocked upstream of the modal.

Severity 2 under §20.3: *"a workflow requires an unreasonable workaround."*
Coordinate-driven automation across half the control surface is exactly that,
and it degrades on every DPI and resolution change — which W11 deliberately
varies (1920×1080 @100%, 1366×768, 150% DPI).

## Caveat — static audit, pending live confirmation

This audit reads source because DEF-0001 leaves no runnable binary to enumerate.
§C.7 specifies a **live** UIA enumeration of `frmLogin` and `frmMain`, which has
**not** been performed. Two mechanisms could move the figure once the app runs:

- controls constructed outside `InitializeComponent` (none found in a search of
  `PharmaX.Desktop`, but absence of a grep hit is not proof);
- a base class or theme pass assigning `Name` centrally — `PhxFormBase` applies
  theme fonts and re-measures layout, and was **not** observed to set `Name`,
  but this was not confirmed at runtime.

The figure is therefore reported as **static-derived and pending live
confirmation**, not as an observed runtime measurement. It must be re-taken
against the live tree as the first action of the re-run W0.

## Remediation note (not applied)

Per Authority rule 3 the agent has not modified source. The fix is mechanical —
one `X.Name = "X";` line per control inside `InitializeComponent`, which the
solution already does 139 times for passive chrome and 160 times for interactive
controls. It is a naming pass, not a redesign, and it is best done before the
first functional wave so that W1–W13 are not written twice.

Build green and all 407 tests still pass after the change.

### Correction 1 — the pre-fix figure was 145, not 146

`colAccount` on `frmJournal` was a **false positive**. It is constructed with
an object initializer that already sets `Name = "Account"`:

```csharp
colAccount = new DataGridViewComboBoxColumn
{
    HeaderText = "Account",
    Name = "Account",      // ← already an AutomationId; the audit missed it
    ...
};
```

The original audit looked only for the statement form `x.Name = "…";` and did
not parse initializer bodies. The audit has since been taught to read them.
Inserting an assignment there also broke the build, which is how it was caught.

### Correction 2 — the audit covered 40 of 46 forms, not all of them

The audit reads `*.Designer.cs`. **Six forms have no designer file** and build
their controls in code, so they were never examined and are **not** included in
the 309:

`frmPrinterSetup` · `frmSystemSetup` · `frmAccountPicker` · `frmAccounts` ·
`frmAttachmentDetails` · `frmPatientAttachments`

Spot-checking `frmPrinterSetup` shows the same defect in a worse form — its
controls are private fields (`_receipt`, `_label`, `_save`, `_cancel`,
`_testReceipt`) with **no `Name` assigned anywhere**, so all five are
unaddressable. `frmSystemSetup` is on the walkthrough's critical path for the
Administrator role.

**These six forms remain unfixed.** The stated 99.0% is 99.0% *of the forms
audited*, and the honest figure across all 46 forms is not yet known. A second
pass must cover code-built forms before this defect is closed.

### Live confirmation obtained

The mechanism is no longer inferred. `frmLogin` was enumerated through UIA3
against the running application and every control surfaced its stable id:

```
layRoot · lblTitle · pnlLogo · lblUsername · txtUsername
lblPassword · txtPassword · pnlButtons · btnLogin · btnCancel
```

The repository's own `docs/signin.ps1` depends on exactly this — it locates
`txtUsername`, `txtPassword` and `btnLogin` by `AutomationId` — which is why
sign-in automation worked before the fix while almost nothing else did.
