## Summary

The merge that caused DEF-0001 brought together **two complete, independently
designed accounting subsystems**, each with its own chart of accounts, its own
posting engine, and its own account-code constants. They were never reconciled.
**The two charts assign different meanings to the same account codes.**

This was not visible until the Application layer compiled. It is the concrete
realisation of the risk recorded in DEF-0001's remediation note: *"resolving it
by deleting either declaration at random would silently change the shape of
posted journal data."*

## The two subsystems

| | Branch A | Branch B |
|---|---|---|
| Posting engine | `JournalPoster` — posts per transaction | `DayEndPostingService` — posts a day in batch |
| Code source | `PharmaX.Domain.Finance.LedgerCode` (constants) | `AccountingOptions` (configurable) |
| Seeder | `ReferenceDataSeeder.SeedChartOfAccountsAsync` **:53** | `…SeedChartOfAccountsAsync` **:257** |
| Seeder behaviour | per-code idempotent, driven by `LedgerCode.Standard` | all-or-nothing (`if AnyAsync return`), hard-coded list |
| Accounts | **14** — full double entry | **9** — no expense, no equity accounts |
| Call sites | ~17 | 4 |

Both seeders are `private async Task SeedChartOfAccountsAsync(CancellationToken)`
in the same class — which is the CS0111 error still blocking the build.

## The collision

**The same account code denotes a different account in each chart:**

| Code | Branch A (`LedgerCode`) | Branch B (seeder :257) | |
|---|---|---|---|
| **1000** | **Bank** | **Cash on hand** | ⚠️ conflict |
| **1010** | **Cash on Hand** | **Card clearing** | ⚠️ conflict |
| **1200** | **Stock on Hand** | **Vouchers redeemed** | ⚠️ conflict |
| 1020 | — | EFT clearing | B only |
| 1100 | Trade Debtors | Trade debtors | ✅ agree |
| 1110 | — | Medical aid debtors | B only |
| 1150 | Medical Aid Debtors | — | A only |
| 2000 | Trade Creditors | — | A only |
| **2100** | **VAT Control** | — | ⚠️ VAT split |
| **2200** | — | **VAT output** | ⚠️ VAT split |
| 3000 / 3100 | Owner's Capital / Retained Earnings | — | A only |
| 4000 | Sales | Sales | ✅ agree |
| 4900 | — | Rounding differences | B only |
| 5000 / 5100 / 5200 / 5900 | Purchases / Stock Written Off / Claims Written Off / Cash Short or Over | — | A only |

Only **two** codes out of nineteen agree.

## Failure scenario — a single cash sale posts to two different accounts

```
JournalPoster    : LedgerCode.For(TenderType.Cash)        -> CashOnHand = "1010"
DayEndPosting    : AccountingOptions.CodeFor(Cash)        -> Cash       = "1000"
```

Whichever seeder survives, one engine posts into an account that means something
else, or into one that does not exist:

**If seeder :53 wins** (chart = `LedgerCode.Standard`, 14 accounts)
- Day-end cash takings post to `1000` → lands in **Bank**, not Cash on Hand.
- Day-end VAT posts to `2200` → **account does not exist in the chart.**
- `1020`, `1110`, `4900` likewise do not exist.

**If seeder :257 wins** (chart = the 9-account list)
- Automatic cash postings go to `1010` → land in **Card clearing**.
- `JournalPoster` VAT posts to `2100` → **account does not exist.**
- Stock postings go to `1200` → land in **Vouchers redeemed**.
- Nine accounts `JournalPoster` needs are missing — including **Purchases** and
  **Trade Creditors**, so a goods receipt cannot post at all.

Either way the result is **a wrong VAT figure and an unbalanced or
misattributed journal**, which §N names explicitly as Severity 1:

> *"A wrong VAT figure, a wrong co-payment, an unbalanced journal, a sold expired
> batch or a dispensing without pharmacist authorisation is **Severity 1**."*

## Why the agent has not resolved it

Choosing a chart of accounts is a **business and accounting decision**, not a
mechanical merge resolution. It determines which ledger every future transaction
posts to, and it cannot be inferred from the code — both schemes are internally
coherent and both are documented as deliberate. Authority rule 2 applies: the
specification does not state the chart (§15.3 defines the *mapping concept*, not
the numbering), so the expected result cannot be derived.

Guessing here would produce a build that compiles and posts silently wrong
financial records — strictly worse than a build that does not compile, because
the failure would not announce itself.

## Recommendation (for the owner's decision, not applied)

**Adopt Branch A (`LedgerCode.Standard`) as the chart, and re-point Branch B's
defaults at it.** Rationale:

1. **It is a complete double-entry chart.** Branch B's 9 accounts contain no
   expense and no equity accounts, so purchases, stock write-offs, owner's
   capital and retained earnings have nowhere to post. A trial balance built on
   it cannot balance a goods receipt.
2. **It carries the larger share of the posting surface** — ~17 call sites
   against 4.
3. **Its seeder is the safer one.** `:53` is idempotent per account code and
   survives a chart that has been added to; `:257` is all-or-nothing and will
   silently skip seeding entirely if any account already exists.
4. **Branch B's configurability is preserved, not lost.** `AccountingOptions`
   stays exactly as it is — only its *default values* change to the `LedgerCode`
   numbers. That keeps the §15.3 promise that the chart is configuration rather
   than constants, which is the genuinely better idea of the two.

Concretely: delete seeder `:257`, keep `:53`, and change `AccountingOptions`
defaults to `Cash="1010"`, `Card="1000"`, `Eft="1000"`, `AccountsReceivable="1100"`,
`MedicalAidReceivable="1150"`, `SalesIncome="4000"`, `VatOutput="2100"` — with
`Voucher` and `Rounding` needing new accounts added to `LedgerCode.Standard`,
since branch A has no equivalent for either.

**That last point is itself a decision:** vouchers and rounding differences exist
in branch B's model and have no home in branch A's. They cannot simply be dropped
— rounding in particular is required for a journal to balance under
`pos.rounding.mode` (Appendix E).

## Impact on the engagement

DEF-0001 **cannot be fully cleared** until this is decided. The build currently
fails with one remaining error (CS0111, the duplicate seeder). Every ACC
requirement, TC-14, and the W7 wave depend on the answer, and any NFR or
functional figure taken before it is settled would be measured against a chart
that may change.
