## Why this is a separate record

DEF-0001 reported six compiler errors. Clearing them revealed that the same
merge had done **three further pieces of damage in two more layers**, none of
which the compiler could see until the layer above it built. This record exists
so the full blast radius of one bad merge is on the record, not just its first
symptom.

## A — `MedicalAidClaimConfiguration` was deleted outright

`PharmaX.Persistence/Configurations/FinanceConfiguration.cs` went from **147
lines to 88**. The merge resolved the file by taking one side wholesale,
discarding the 52-line `MedicalAidClaimConfiguration` that commit `d38619e`
("Bill the medical aid schemes for what they owe") had added.

**Effect:** EF Core could not build the model at all.

```
System.InvalidOperationException : The property 'MedicalAidClaim.Claimed'
could not be mapped because it is of type 'Money', which is not a supported
primitive type or a valid entity type.
```

**This is worse than a test failure.** Model validation runs on first
`DbContext` use, so the *application itself* would have thrown on the first
screen that touched the database. The product was not merely untested — it was
unrunnable.

**Evidence it was deletion, not absence:** every migration snapshot in the
repository still configures the property —
`PharmaXDbContextModelSnapshot.cs:157` carries
`b.ComplexProperty<…>("Claimed", "…MedicalAidClaim.Claimed#Money", …)`. The
migrations were generated from a model that had the configuration; the runtime
model no longer did.

**Fix applied:** the deleted class was restored verbatim from `d38619e`. No
shape was invented — the migration snapshots already fixed the expected
mapping (`Claimed`/`Settled`/`WrittenOff` each as a complex property with
`Amount` and `Currency` columns), and the restored code produces exactly that.

## B — Three `DbSet` properties declared twice

`PharmaXDbContext.cs` declared `LedgerAccounts`, `JournalBatches` and
`JournalLines` twice — once with `using`-resolved short names, once fully
qualified as `Domain.Finance.X`. With `using PharmaX.Domain.Finance;` present,
the two forms resolve to the **same types**, so this was a pure duplicate.

**Fix applied:** the fully-qualified block was removed, keeping the short-name
form used by the rest of the file. No semantic change.

## C — Two migrations create the same three tables

Both branches generated a migration creating the ledger schema:

| Migration | Branch | Tables | Indexes |
|---|---|---|---|
| `20260911131247_Journals` | A | JournalBatch, LedgerAccount, JournalLine | 4 |
| `20260913133523_Accounting` | B | JournalBatch, LedgerAccount, JournalLine | 6 |

Merged into one linear history, the second fails:
`SQLite Error 1: 'table "JournalBatch" already exists'`.

**Which is correct is determinate, not a judgement call.** The model snapshot —
the authority on the current model — carries **4** indexes across the three
tables (JournalBatch 2, JournalLine 1, LedgerAccount 1), which is exactly what
`Journals` creates. `Accounting` creates a different set and **omits** the
composite unique index `(JournalBatchId, LineNo)` that the surviving
`FinanceConfiguration.cs:86` requires.

**Fix applied:** `20260913133523_Accounting` and its host twin
`20260913133531_HostAccounting` (and both `.Designer.cs`) were removed as stale.
Safe because no database has ever had them applied — the build has been broken
since the merge, and cutover (MIG-015) is not until 31 October 2026.

## D — `DayEndPostingService` violated the architecture test

`PharmaX.Tests.Unit.Architecture.DocumentSeriesTests.Nothing_asks_for_a_series_by_literal`
failed: `DayEndPostingService.cs:167` called `NextAsync("JNL", ct)` with a
literal where `DocumentSeries.Journal` already exists. Branch B's service
predated branch A's constant, and the merge put them in the same solution
without reconciling them.

**Fix applied:** `NextAsync(DocumentSeries.Journal, ct)`.

This is the architecture test earning its keep — it caught a merge artefact that
no compiler and no functional test would have.

## Standing recommendation

One merge produced defects in four layers and two of them were invisible until
the layer beneath compiled. The compiler found three, the **integration tests**
found one, and the **architecture test** found one. That is a strong argument
for a CI gate that builds and runs both test tiers on every merge to `main` —
`main` has been unbuildable since `37ac703` and nothing reported it.
